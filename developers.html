Comprehend is the ambient AI that listens to the PT visit and writes the note inside the EMRs clinics already use. Bring your app in — as it is — and two things happen: what you know about the patient lands in the clinical record, in every EMR; and what happened in the room comes back to you, per patient, the moment the note is written.

What it looks like in the note

Your markdown lands in the visit's Clinical Facts and the note is written with it in view. A typical daily note, with your data in it:

Subjective
Pt reports completing home program 5 of 7 days this week; skipped hip hinge x3 due to knee pain,
pain trending 6 → 3 over the week per remote monitoring. (Source: Your App)

Plan
Reviewed RTM data with patient and discussed adherence barriers (knee pain with hip hinge);

The PT didn't type any of that. You provided the first half. The second half is what happened in the room — and it comes back to you as answers, in the shape you asked for.

How it works

Your existing app opens inside Comprehend as a panel next to the clinician's note — in the web app and in the Chrome side panel inside the EMR. Same UI, same login. A hosted script gives it a comprehend object with three things: events we send you, content you give us (that's what reaches the chart), and questions you ask (that's what comes back from the room).

1

Load the script

On the page you want to embed. Vanilla JS; works in any framework.

<script src="https://app.comprehendpt.com/comprehend.js"></script>
2

Handle the patient

One callback. Comprehend hands you a patient handle — who it has open — with a reason: ready (your frame just loaded), changed (the clinician switched charts), refresh (the clinician is about to generate a note, or pressed Refresh). Find that person in your system (or offer to create them), open their chart in your UI, and once it's up, tell Comprehend what you know and ask your questions. Same code path every time. If the clinician picks a different patient inside your app, call setContext again from the same place.

comprehend.on('patient', async function onPatient(patient, { reason }) {
  if (!patient) return;                        // Comprehend has no chart open
  // patient = { id, name, dob, yourId, setContext(), clearContext() }

  // ---- your business logic -------------------------
  let mine = byId(patient.yourId) || byName(patient.name);   // who this is in YOUR system
  if (!mine) {
    // Not in your system yet — offer to create them from what Comprehend knows.
    mine = await offerToCreatePatient({ name: patient.name, dob: patient.dob });
    if (!mine) return;                        // the clinician said no; wait for the next patient event
  }

  openChart(mine);                               // navigate your UI to this patient …

  onChartLoaded(mine, () => {                    // … and once that page is up, tell Comprehend what you know.
    // This call is also what links the two records — next visit, patient.yourId === mine.id.
    patient.setContext(`## Home program — last 7 days
- Adherence: ${mine.adherence}
- Pain trend: ${mine.painTrend}`, { id: mine.id, name: mine.fullName });

    askAboutTheVisit(mine);                      // step 3
  });
});
3

Ask about the visit

Two arguments: the structure you want back and a callback that receives it filled in. Keys are your names. A plain string is a free-text question; add _type, _choices or a nested branch when you want the answer constrained. Build it from the patient's own data — one yes/no per prescribed exercise, choices from the exercises you actually assigned — and call it again when the patient changes.

let unsubscribe;
function askAboutTheVisit(mine) {
  if (unsubscribe) unsubscribe();               // questions are per patient
  unsubscribe = comprehend.subscribe({
    performed: {                                 // nest as deep as you like
      _description: 'Only what was done or reviewed in the room today',   // context for a whole branch
      'Sit-to-stand': { _type: 'boolean' },        // yes / no
      'Hip hinge':    { _type: 'boolean' },
    },
    pain_today: {
      _type: 'integer',
      _description: '0-10 as the patient reported it, or null',
    },
    symptoms: {                                  // pick any
      _choices: ['pain', 'stiffness', 'swelling', 'giving way'],
      _multiple: true,
    },
    plan: {                                      // pick one
      _choices: ['progress', 'hold', 'regress', 'discharge'],
    },
    changes: [{                                  // a list — one row per change the PT stated
      exercise: { _choices: mine.program },      // from YOUR data — where answers get sharp
      dosage:   'sets x reps or time, if stated',   // a plain string: free-text answer
    }],
    patient_said: 'what the patient said about doing the home program',
  }, (answers) => render(answers));
}
// answers → {
//   performed: { 'Sit-to-stand': true, 'Hip hinge': false },
//   pain_today: 3, symptoms: ['pain'], plan: 'progress',
//   changes: [{ exercise: 'Hip hinge', dosage: '2x10' }],
//   patient_said: '…',
// }

Nothing specific to ask yet? Ask for nothing. An empty structure — {}, '' or null — gives you one plain-text summary of the visit as it relates to your app, given the context you set. A string, not an object; empty when nothing relevant was said.

comprehend.subscribe({}, (summary) => show(summary));
// summary → "Patient reported doing the program most days but skipped hip hinge
//             because of knee pain; PT regressed it and progressed sit-to-stand to 3x12."

Ready, without a ready event

The first patient event fires exactly once per load, first, with reason: 'ready' — even when no chart is open (patient is null). Register callbacks whenever you like: before the handshake they queue; after it, a new listener is called immediately with the current state. Nothing can be missed.

Shape in, shape out

Nest branches, put a _description on a leaf or a whole branch, constrain with _type (boolean, integer, number, string) or _choices (+ _multiple for pick-any), and use a one-row array for a list sized to the transcript.

Push, not poll

You never ask on a timer. We compute when the clinician acts and cache when nothing changed. Every answer names the patient it's for.

The API

Two events, two content calls, one question call. That's all of it.

Events — we tell you
comprehend.on('patient', (patient, { reason }) => …)patient is a handle { id, name, dob, yourId, setContext(), clearContext() } or null when no chart is open. reason is ready (fires exactly once per load, first, even with null), changed, or refresh. Late listeners are called immediately with the current state. yourId is the id you gave setContext last time — stored on our patient record, so it survives devices and sessions; short-circuit on it.
comprehend.on('error', ({ code }) => …)Codes only: STALE_PATIENT, CONTEXT_REJECTED, BAD_STRUCTURE, TOO_MANY_SUBSCRIPTIONS. Reasons and names go to the clinician, not to you.
Content — you tell us
patient.setContext(markdown, { id, name })Replaces your context for that patient. Markdown, ≤ 8 KB. { id, name } is your patient; name is required and must resemble the chart's name; id comes back as yourId next time. The handle carries our patient id for you — a handle from a chart the clinician has left is dropped with STALE_PATIENT.
patient.clearContext()Withdraws your content; the link is kept.
Questions — you ask
comprehend.subscribe(structure, (answers, patient, meta) => …)Registers a question structure; returns unsubscribe(). Answered on clinician action; meta is { version, partial, errors }. Up to 10 live subscriptions, 200 leaves each. Build it per patient.
comprehend.patientThe current handle, or null, for whoever wants to pull.

Structures

A structure is a nested object whose shape is the answer shape. A plain string leaf is a free-text question. An object leaf constrains the answer: _type (boolean | integer | number | string), _choices (add _multiple: true for pick-any), _description — which also works on a branch, once, for context. An array with one prototype row is a list, sized to what the transcript supports. Fill _choices from your own data — that's where the answers get sharp.

Trust model

Clinician-initiated, always

Answers are computed inside the clinician's session, on their action. Never on a timer, never from your servers. Closing the tab ends access.

Identity is the origin, plus the frame

A clinic admin registers your app's exact origin. We accept messages only from that origin, and only from the frame we created for you. No tokens to manage. Several apps may share an origin if their launch URLs differ.

Linking is a human act

Nobody fuzzy-matches names. The clinician opens the same patient in both places; your first setContext is the link, and we check the names resemble each other before we accept it. If they don't, you get CONTEXT_REJECTED and the clinician gets told which two names disagreed.

BAA before anything loads

A clinic admin cannot enable your app until they confirm their organization holds a signed BAA with you — and they're told exactly what they're sharing. Your page never loads, and never receives a patient name, before that. Have your BAA ready.

Describe your app once — the manifest

Host a small JSON file at https://<your origin>/.well-known/comprehend-app.json. It is what a clinic admin sees when they paste your link: no fields to fill in, no origins to type. Every key is optional; without the file we show your hostname as the name and use the pasted link as-is. launchUrl must be on the same origin as the manifest; URLs may be relative to the manifest file. Can't serve /.well-known/? Give the clinic a link to the manifest itself — a pasted link ending in .json is read as the manifest — or they can type its URL under Advanced. The sandbox's Check my app shows you exactly what admins will see. Filled-in examples: hep-rtm.json, force-plate.json (why they aren't at the root).

Requirements

  • Your launch URL must be https and framable by Comprehend — the web app and the Chrome extension's side panel: Content-Security-Policy: frame-ancestors https://app.comprehendpt.com chrome-extension://pjafhckheppfdbidlhoedddfgebmcmnc (no X-Frame-Options: DENY). The sandbox's Check my app verifies both from our server.
  • Publish a manifest at /.well-known/comprehend-app.json so admins see your name, description and BAA contact instead of a hostname. Optional, strongly recommended; required for a directory listing.
  • Your login must work inside a frame on our origin. Your session cookie is a third-party cookie there, so SameSite=Lax cookies are not sent and the app appears logged out. Mark the session cookie SameSite=None; Secure; Partitioned (CHIPS), or sign in via a popup (we allow popups). This is the one thing that bites first integrators.
  • We append ?comprehend=1 to the launch URL so you can render an embedded layout.
  • Load the script from https://app.comprehendpt.com/comprehend.js — don't vendor a copy; it pins the host origin and evolves with the contract.
  • Handle patient being null and yourId being absent. Show "Comprehend: Ann K." next to your open chart so a mismatch is visible.
